# Decision log

Format: ID, status (accepted / proposed / superseded), context, decision, consequences.
Add new decisions at the bottom. Never delete; supersede instead.

## ADR-001: Script first, render second (accepted)
- Context: Recording a screen and then narrating it makes sync fragile.
- Decision: Generate the review and script first, synthesize audio, measure durations,
  then choreograph the browser to match.
- Consequences: Exact sync; the video is deterministic given the same inputs.

## ADR-002: Agents only where judgment is needed (accepted)
- Decision: Reviewer, Verifier and Narrator are agents. Ingest, TTS, Director, Recorder,
  Composer and Publish are plain code.
- Consequences: Lower cost, fewer flaky failures, easy unit testing.

## ADR-003: JSON Schema is the cross-stage contract (accepted)
- Context: Contracts must be readable by humans, prompts, tools and any implementation.
- Decision: `schemas/*.schema.json` are the source of truth. See ADR-011 for how the
  TypeScript implementation derives types and validators from them.
- Consequences: Contracts survive a language change; golden fixtures validate both.

## ADR-004: Kokoro via Kokoro-FastAPI container (accepted)
- Context: Kokoro runs locally in Docker; the same setup must work in CI.
- Decision: TTS provider calls the container's OpenAI-compatible HTTP endpoint.
  Piper (via its CLI or an HTTP wrapper container) is the fallback; paid providers are optional.
- Consequences: No ML dependencies inside the tool; any OpenAI-compatible TTS can be
  swapped in by config. Image name and tags must be pinned and verified.

## ADR-005: diff2html as the default renderer (accepted)
- Decision: Render a local HTML page from the diff instead of driving the GitHub UI.
- Consequences: No login, stable selectors, theming control, works for pushes without a
  PR. GitHub page mode stays optional.

## ADR-006: Review the target stack with a dedicated rubric (accepted)
- Decision: The Reviewer prompt is built from `docs/REVIEW_RUBRIC.md`
  (TypeScript, NestJS, DDD, event-driven, PostgreSQL).
- Consequences: Rubric changes are prompt changes and must be re-evaluated on the golden set.

## ADR-007: PR-level review by default; push-level optional (accepted)
- Context: Reviewing every push produces many videos and duplicates PR runs.
- Decision: See the trigger policy in ARCHITECTURE.md section 3.
- Consequences: Lower cost and less noise; branches without PRs can opt in.

## ADR-008: Video hosting (proposed)
- Context: GitHub's API cannot attach a video file to a comment.
- Options:
  1. Actions artifact, linked from the comment. Free; viewers must be signed in and
     download it; retention is limited.
  2. S3-compatible object storage (for example Cloudflare R2 or AWS S3) with a presigned
     or public URL. Plays in the browser; small storage cost.
  3. Release asset on a dedicated pre-release. Free; clutters releases; visibility follows
     the repository.
- Proposal: Option 1 for Milestone 4, Option 2 once playback in the browser matters.

## ADR-009: Implementation language is TypeScript (accepted, September 2026)
- Context: The tool was first planned in Python. The team works in TypeScript/NestJS, and
  with Kokoro behind HTTP nothing requires Python. Playwright, the Anthropic SDK, Octokit
  and diff2html are all first-class in Node.
- Decision: Node.js LTS, TypeScript strict, ESM, pnpm, Commander for the CLI, vitest for tests.
  No NestJS inside the tool: it is a CLI pipeline, and plain modules keep it light.
- Consequences: The team can maintain it; one language across services and tooling.
  The Python stack in earlier drafts (uv, Pydantic, Typer, pytest) is superseded.

## ADR-010: ORM assumed in samples (proposed)
- Decision: Golden samples assume TypeORM. Replace with Prisma/MikroORM patterns if the
  services use those; labels and schemas are unaffected.

## ADR-011: Types and validation from JSON Schema (accepted)
- Context: ADR-003 makes JSON Schema the contract. The TypeScript code needs both static
  types and runtime validation without two definitions drifting apart.
- Decision: Generate types with `json-schema-to-typescript` into
  `src/contracts/generated/` (committed, regenerated by `pnpm gen:types`, checked in CI).
  Validate at runtime with Ajv (draft 2020-12 build). Cross-field rules live in
  `src/contracts/checks.ts`. The same schemas are passed to the LLM as the required output
  shape and as tool input schemas.
- Alternative considered: Zod as the source with JSON Schema exported from it. Rejected
  to keep the language-neutral files authoritative.
- Consequences: One definition per contract; validation errors from Ajv are fed back to the
  model on retry.

## ADR-012: Toolchain versions (accepted, September 2026)
- Context: TypeScript 7 is released, but typescript-eslint 8.x supports TypeScript below 6.1.
  pnpm 12 fails installs when dependencies with build scripts are not approved, and
  holds back very recently published versions by default.
- Decision: Pin `typescript` to `~6.0.3` until typescript-eslint supports 7. Use pnpm 12
  (`packageManager` field), approve only `esbuild` builds in `pnpm-workspace.yaml`, and
  keep the release-age protection on. Node.js 22.13+ (required by ESLint 10 and vitest 5).
- Consequences: Revisit when typescript-eslint supports TypeScript 7. New dependencies with
  install scripts must be approved explicitly in `pnpm-workspace.yaml`.

## ADR-013: Pin corepack when enabling pnpm (accepted, September 2026)
- Context: The corepack bundled with some Node.js 22 releases is too old to run pnpm 12
  (confirmed on a developer machine; it worked with corepack 0.36.0). The bundled version
  differs between Node releases and machines, so a bare `corepack enable` is not reliable.
- Decision: Install a pinned corepack before enabling it, locally and in CI:
  `npm install -g corepack@0.36.0` then `corepack enable`. corepack 0.36 requires
  Node.js 22.22.2 or newer on the 22 line.
- Consequences: CI and local setup behave the same. Bump the pin deliberately. Newer Node.js
  majors no longer bundle corepack, so the explicit install also keeps future upgrades working.

## ADR-014: ingest.json is a cross-stage contract (accepted, September 2026)
- Context: The Verifier, Director and Recorder all need to know which files and lines exist
  in the reviewed diff. Re-parsing the patch in each stage would duplicate logic.
- Decision: The Ingest stage writes `diff.raw.patch` (input as received), `diff.patch`
  (kept files only) and `ingest.json` (source, kept and skipped files, and a line index of
  every hunk), validated by `schemas/ingest.schema.json`. A small in-house parser handles
  git-format unified diffs (renames, copies, deletions, binary markers, mode changes, quoted
  paths, "No newline at end of file"); no diff-parsing dependency. `ingest.json` has no
  timestamps, so re-running ingest on the same input gives identical bytes.
- Consequences: Later stages read `ingest.json` through one `HunkIndex` API. Pull request
  input (`--pr`) arrives in Milestone 4 and must produce the same files.
